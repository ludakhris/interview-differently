# Learner outcomes, talent, attendance and activity (#69): design and contract

This is the contract the feature agents follow. Types are in `packages/types/src/{outcomes,talent,attendance,activity}.ts` (copied into the API by `npm run sync:types --workspace @id/api`). Anything in a response shape here that differs from those files is a bug in this document; the types win.

## 1. Scope rule

Notes and support items belong to **(providerId, userId)**. `providerId` is `Course.providerId` of the cohort the person is in. They follow the participant across all of that provider's cohorts (whichever workspace hosts the cohort) and never cross providers. A person in two providers' cohorts has two separate sets.

The **talent profile is about the person, not a provider**: there is exactly one per user, and it does not differ per program. The learner decides **who may see it** from a list of organizations built from their own enrollments (`ProfileShare`, one row per organization they chose). Staff of provider P read the content of a person's profile **only if that person has a `ProfileShare` for P**; otherwise they get status only (does a profile exist, is it complete, is it fresh). A share for another organization never lets P see it.

"Participant of a provider" means an enrollment of any status in a cohort whose course has that provider (`ProviderAccessService.assertParticipantOfProvider`). Withdrawn people keep their notes and their sharing choice.

A cohort can **require** the profile (`Cohort.requiresProfile`) and set a **refresh period** (`Cohort.profileRefreshMonths`, 1-60, null = never goes stale). A requiring cohort puts "Your profile" first in the learner's course and makes it required for completion (see 6C).

Resume objects of dropped rows are not deleted from storage (orphans).

## 3. Access matrix

Roles are the Clerk `publicMetadata.role` (`LEARN_ROLES`). "Staff of provider P" = role `provider-admin` AND a workspace-level `Membership` (cohortId null) on institution P of kind `provider` (`assertProviderStaff`). An **organization** that hosts cohorts is treated the same way for the people in the cohorts it hosts: its staff are `provider-admin` with a membership on the organization, and notes, support items, profile shares and the access log are keyed to the organization itself (column "Organization staff", read "staff of that organization, for its own hosted cohorts"). The two scopes are separate: a provider's notes are never shown to an organization that runs its course, and the reverse (`institutionCohortWhere`, `ProviderAccessService.scopeForCohort`). System admin passes everything.

| Data                              | Learner (self)                     | Staff of provider P                                                                                | System admin | Organization staff                                       | Agency admin            | Staff of other provider | Case manager |
| --------------------------------- | ---------------------------------- | -------------------------------------------------------------------------------------------------- | ------------ | -------------------------------------------------------- | ----------------------- | ----------------------- | ------------ |
| Notes, support items              | never                              | read/create/update/delete                                                                          | yes          | yes, its own                                             | no                      | no                      | no           |
| Compensation, resume              | own: read/edit                     | read, export (no edit) **only if the learner shared the profile with P**                           | yes          | yes, only if shared with the organization                | no                      | no                      | no           |
| Talent profile (non-compensation) | own: read/edit                     | content: read, export (no edit) **only if shared with P**; status (exists, complete, fresh) always | yes          | yes, only if shared with the organization; status always | no                      | no                      | no           |
| Data access log                   | no                                 | own provider's                                                                                     | any          | its own organization's                                   | no                      | no                      | no           |
| Attendance (cohort)               | own marks read-only, no staff note | roster guard (`assertCohortStaff`)                                                                 | yes          | roster guard                                             | roster guard (in scope) | roster guard            | no           |
| Activity (cohort)                 | own totals                         | roster guard                                                                                       | yes          | roster guard                                             | roster guard (in scope) | roster guard            | no           |
| Outcomes (A)                      | own only                           | n/a                                                                                                | n/a          | n/a                                                      | n/a                     | n/a                     | n/a          |

Roster guard = `assertCohortStaff(userId, role, cohortId)`: role in `agency-admin | provider-admin` (or system admin) and the caller may open the cohort's host workspace (`LearnService.assertWorkspace`). It is the same rule as `LearnCohortsService.cohortFor`. So a provider's own staff reach attendance and activity of a cohort hosted by an organization only if they are also members of that organization; talent data they reach through the provider scope.

Rules that follow from the matrix:

- No learner endpoint may ever select from `ParticipantNote`, `SupportItem` or `DataAccessLog`, and the learner profile endpoints must not return anything staff wrote. Each feature has a test that a learner (no role) gets 403 on every staff endpoint and that learner responses carry none of those fields.
- Compensation fields (`previousCompensation`, `targetCompensation`) must never appear in: list rows, any agency or workspace rollup, any `outcomes`/`gradebook`/exit-file payload, log `detail`, error messages, or server logs. They appear only in the learner's own profile, in the response of the staff `GET .../compensation` endpoint (fetched only when staff click Show compensation, and only if the profile is shared with that provider), and in the CSV export (opt-in, shared profiles only). The staff `/profile` response never carries them; it has `hasCompensation` instead.
- Resumes are in `PRIVATE_MEDIA_STORAGE` only; the DB holds the key. Key format `talent/resumes/{userId}/{uuid}-{safeName}` (resumes uploaded before 2026-10-11 keep their old `{providerId}/{userId}` key). Downloads are short-lived signed URLs (300 s). Never a public URL.
- Every staff-endpoint handler begins with its access check, then validates that the target participant belongs to the provider (`assertParticipantOfProvider`), then reads. Profile content is read only after the share for that provider is confirmed; an unshared profile's fields are never selected for output.

## 4. Audit rules

`DataAccessLogService.record({actorId, providerId, subjectUserId?, resource, action, detail?, actorName?})`, **awaited before the response is built**. If the log write fails the request fails (nothing is read untraced).

| Staff request                                            | Rows written                                                                                                                                                                                     |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| list notes of a participant                              | `note` / `list`, subject                                                                                                                                                                         |
| create / update / delete a note                          | `note` / `create`, `update`, `delete`, subject                                                                                                                                                   |
| list a participant's support items                       | `support_item` / `list`, subject                                                                                                                                                                 |
| create / update / delete a support item                  | `support_item` / `create`, `update`, `delete`, subject                                                                                                                                           |
| provider-wide support queue                              | `support_item` / `list`, no subject, detail `queue, N rows`                                                                                                                                      |
| view a participant's profile                             | `talent_profile` / `read`, subject, **only when content is returned (shared)**. A status-only response (`not_shared`, `none`) writes none. Never a compensation row; the response carries no pay |
| reveal a participant's compensation                      | `compensation` / `read`, subject, awaited before the amounts are read (a failed write fails the request and returns nothing)                                                                     |
| download a resume                                        | `resume` / `download`, subject                                                                                                                                                                   |
| export profiles (CSV)                                    | `talent_profile` / `export`, no subject, detail `csv, N rows, shared profiles only[, M not shared left out]`; plus `compensation` / `export` when compensation columns are included              |
| search that filters or returns only non-sensitive fields | none                                                                                                                                                                                             |

`detail` is at most 200 characters and holds counts or formats only, never note text, amounts or file content. Resource and action values are the unions in `talent.ts`. Reading the log: `GET /learn/data-access-log?providerId&subjectUserId&actorId&resource&limit&before` (system admin: any or all providers; provider staff: `providerId` required and must be their own) returns `DataAccessLogPage`. Reading the log itself is not logged.

## 6. Endpoints

All under the API prefix, all behind `LearnGuard`. Errors use Nest exceptions with plain-language messages (403 no access, 404 not found, 400/409 validation, as the existing services do).

### A. Learner outcomes (agent A, `outcomes/`)

`GET /learn/me/outcomes` -> `LearnerOutcomes`. Any signed-in learner; only the caller's own enrollments (withdrawn excluded). Reuse `readiness`/`skills` logic from `learner.service.ts`/`outcomes.ts`/`skills.ts`. No compensation, no staff data.

Response notes (fix pass): `items` holds each ordinary item plus a "Review: ..." row for content a learner must redo (`review: true`); the pre-check carries `preCheck: true`. The average score on the page is the mean of the best score on each scored item, counted once (reviews and the pre-check left out). `totals.attempts` is the attempts on scored items. `hasInterview` says whether the course has anything that counts as an interview: only then does completion need interview readiness, so the page never asks for a practice interview otherwise.

Nav and routes (web): Talent, Support and `/lms/talent/*` need provider-admin or system-admin in a provider or organization workspace; Activity and `/lms/activity` need agency-admin, provider-admin or system-admin in a provider or organization workspace. The role comes from the Clerk public metadata (`useRole`), as for Admin. Anyone else, and agency workspaces, get a "Page not found" notice for those routes. The API stays the real gate.

All learner profile responses are `Cache-Control: no-store`. The storage key is never returned.

Validation: whole dollars `0..10_000_000`; years `0..60`; graduation year `1950..2100`; text <= 200; lists (industries, targetRoles) are real arrays of <= 20 entries of <= 80 characters (a comma-separated string is a 400); `educations` <= 8, each `{level, fieldOfStudy?, school?, graduationYear?}` with `level` one of `EducationLevel`; `shares` is the **complete set** of organizations to show the profile to, every `institutionId` must be in the learner's own `organizations` (otherwise 400 `Choose organizations from your list.`); an organization in `organizations` but not in `shares` is not shared. Error messages never repeat an amount.

**Computed `complete`:** at least one education entry (with a level), `yearsExperience` present (0 counts), at least one industry, at least one target role (**both required**), **and an uploaded resume**. `completedAt` is set the first time a save **or a resume upload** leaves the profile complete and is kept after that (a later edit or a resume removal can make `complete` false again). Staff-facing `complete` (status, participant rows, export) uses the same definition. No migration: profiles saved before these rules read as incomplete until they have a resume and BOTH an industry and a target role (a profile with only one of the two was complete before, and is not now). A save always moves `updatedAt`, so saving an unchanged profile is how a learner confirms it is current.

`ShareOption`: built from the learner's own enrollments (any status) as the provider of each cohort's course (`why: 'your program'`) and the hosting organization (`why: 'your cohort host'`); only institutions of kind `provider` or `organization` are offered. `required` = a non-withdrawn cohort of theirs that requires the profile is run by that organization; it is information for the page, not a forced share (staff still see status without a share). `shared`/`allowEmployers` are the learner's current choice.

`ProfileRequirement` (one per non-withdrawn cohort that requires the profile): `refreshMonths`, `satisfied` (complete, resume included, AND, when `refreshMonths` is set, `updatedAt` + `refreshMonths` calendar months is in the future), `dueBy` (that moment, or null when there is no period or no profile).

**My profile status rail.** One status line ("Almost there: add ..." listing what is missing including "a resume", "Ready to save" only while there are unsaved changes, else "Profile complete") and a dynamic five-item checklist under the label "What counts as complete:", indented (an education entry, your years of experience, at least one industry, at least one job you want, a resume): done items are green with a check and a visually hidden "Done", open ones are an empty circle with "Still needed". The resume item follows the upload/remove response at once, without a save. A requirement shows nothing when met; when not met, one plain line ("Your course needs your profile: finish it." / "Time to refresh your profile: it is due <date>.") with the cohort name in small text and never the organization as a heading. The Resume section carries the "Needed" tag. Section order: Resume, Education, Work experience (years, industries, jobs you want, "Earliest date available for new position"), Salary targets ("What you earned upon sign up (per year)", "What you hope to earn (per year)", with a short "why we ask" paragraph), Who can see this profile (how the data is used, an info callout about changing preferences at any time, then the per-organization boxes).

**The requirement in the course.** `LearnerService.outline` / `cards` / `item` / `evaluateCompletion` and the outcomes service all use one rule (`talent/profile-requirement.ts`):

- Cohort does **not** require it: nothing changes, except that a course's own `profile` items are done by the profile state (complete, no refresh rule) instead of a progress row.
- Cohort requires it: the outline gets a first module titled "Your profile" with one item of type `profile`: the course's own first `profile` item (taken out of its module, which is dropped if that leaves it empty) or, if the course has none, a synthetic item with id `profile` (open it with `GET /learn/me/cohorts/:cohortId/items/profile`; 404 when the cohort does not require it). It is required for completion, counts in `itemsTotal`/`itemsDone` and in `evaluateCompletion` (one extra required item for the synthetic one), and is `completed` when satisfied, `in_progress` with `note` "Finish your profile" / "Time to refresh your profile" when there is a profile that is incomplete or stale, and `not_started` when there is none. `note` is on `LearnerOutlineItem` and `LearnerItem`.
- `LearnerService.syncProfileState(userId)` runs after every profile save and every resume upload or removal (a resume is part of "complete"): for each open (started, not ended) enrollment whose cohort requires the profile or whose course has a profile item, and where the profile is satisfied, it mirrors a finished progress row for the course's own profile items (only so staff rollups that count progress rows agree; learner-facing code never reads it) and asks whether the completion rule is now met. A completed enrollment is never reopened by a profile going stale.

| `GET /learn/cohorts/:cohortId/attendance`                         |                                                                                              | `AttendanceSummary`                                                                                                                                          |
| `GET /learn/cohorts/:cohortId/attendance.csv`                     |                                                                                              | `text/csv` (UTF-8 BOM): name, email, present, absent, late, excused, sessions_counted, sessions_held, rate_percent (a number, empty when none)               |
| `GET /learn/cohorts/:cohortId/sessions/:sessionId/attendance.csv` |                                                                                              | CSV for one session: `name,email,status,marked_at,note` (staff only). Learner: `GET /learn/me/cohorts/:cohortId/attendance` -> `LearnerAttendance` (guard `assertLearnerOfCohort`; own marks only; staff `note` never included). Attendance is not audit-logged (not in the sensitive set); it is covered by the roster guard.

Rate: `(present + late) / (counted sessions - excused)`; `null` when the denominator is 0. A session counts for a learner only if (1) its `startsAt` has passed, (2) at least one mark exists for it (the register was taken; until then the summary and the learner's line say "not taken yet"), and (3) the learner's `Enrollment.enrolledAt` is before `startsAt` (otherwise "before you joined"). Within a counted session a learner with no mark is absent; excused is left out of the denominator. `sessions_held` is every session that has started, counted or not. `PUT .../marks` returns the fresh sheet; concurrent saves are last-write-wins per learner and the UI shows "Saved at HH:MM".

### E. Activity logs (agent E, `activity/`)

Learner write (guard `assertLearnerOfCohort`, cohort not withdrawn):

`POST /learn/me/activity/heartbeat` body `HeartbeatInput` -> 204. Time is active time (idle time is not counted). Server rules (the client cannot inflate time): find the learner's latest page `ActivitySession` (any item) on today's UTC `day`; every beat is measured against that latest beat, so two tabs cannot earn more than elapsed time. If `now - lastSeenAt <= 90 s` and the item is the same, add `min(gap, 60)` seconds and set `lastSeenAt = now`; if the item differs, open a row for the NEW item with `seconds = min(gap, 60)` (a conditional update on the latest row claims the beat first, so two tabs switching together credit it once); a gap over 90 s opens a new row with `seconds = 0`. Ignore (204, no write) beats under 10 s apart, an `itemId` not in the cohort's course, and a cohort whose `endsAt` has passed by more than a day. Client: every 30 s while `document.visibilityState === 'visible'` and there was input within the last 60 s; none while hidden or idle.

Connected tools (no `ItemProgress` write at launch, no schema change): at launch, `LtiPlatformService.startLaunch` (after the learner, cohort and tool are authorised, and never for an unavailable tool) calls `ActivityService.openToolLaunch(enrollmentId, userId, itemId)` as a best-effort side effect (not awaited, errors swallowed, so it cannot slow or fail a launch). It writes one `ActivitySession` row, `kind: 'tool'`, `estimated: true`, `seconds 0`, `startedAt = lastSeenAt = now`; a row with `lastSeenAt = startedAt` is open. A repeat launch within 4 h of an open row reuses it. At score return, `recordToolResult` calls `closeToolLaunch(enrollmentId, itemId)`: the latest open row started within 4 h gets `seconds = min(now - startedAt, 4 h)` (never negative) and `lastSeenAt` moved past `startedAt` (closed), split at UTC midnight (later parts as extra rows). A score with no open launch row writes nothing, and a repeated report finds the row closed, so time is never double counted.

#### How time is collected

There is one concept of time: a **session** has a start (stored in UTC) and a duration (seconds of active time). Two sources feed it, and reports read both the same way.

- **Platform session time.** The learner pages (every `/lms/learning/*` page) record active time with a heartbeat while the learner is on any learning page, the page is visible and there was input in the last minute. A gap longer than the heartbeat window (90 s) ends a session; the next beat starts a new one.
- **Activity time.** Opening an item starts an activity span (a row for that item). Leaving the item, finishing it, or returning from a connected tool ends it. The span's duration is the active time on that item. For a connected tool the span is launch to score return, because that tool runs in another window and the platform cannot see inside it.

Honest limit: time inside a connected tool is launch-to-return (at most 4 hours per launch) unless the tool reports its own time, which the platform does not read today. It can therefore include idle time in the tool, and it can overlap a course page that stays open in another tab. The storage keeps the internal `estimated` column to tell tool rows from heartbeat rows; no report, type or CSV exposes it, and tool rows add into the same totals. In the per-learner log a tool row is just an activity named after the item, with its start and duration.

Every duration is a whole number of seconds; UTC is the storage format only.

#### Timezones

Times are stored in UTC and shown in the viewer's timezone. Every report and CSV request sends `tz` (an IANA name from `Intl.DateTimeFormat().resolvedOptions().timeZone`). The server validates it (`400` for an unknown name, default `UTC`), and buckets days in SQL with `(startedAt AT TIME ZONE 'UTC' AT TIME ZONE tz)::date` (`startedAt` is a zoneless UTC timestamp, so it is read as UTC first). A session that crosses local midnight is attributed to the day it started. `from`/`to` and the report's `day` values are dates in that timezone; the default range is the last 30 days ending today in that timezone. `tz` is passed as a bound parameter, never spliced into SQL. A UTC-day filter on the indexed `day` column (one day either side) narrows the scan.

Staff (guard `assertCohortStaff`; `from`/`to` are YYYY-MM-DD in `tz`, default last 30 days, max range 366 days; not audit-logged):

| Method and path                                                     | Response                                                                                                                                                                                                |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /learn/cohorts/:cohortId/activity?from&to&tz`                  | `CohortActivityReport`: `totalSeconds`, `averages`, `days`, `learners` (each with `averagePerActiveDaySeconds`), `items`                                                                                |
| `GET /learn/cohorts/:cohortId/activity/learners/:userId?from&to&tz` | `LearnerActivityReport` (404 unless enrolled in the cohort): `days` with first start, last activity end, total, `sessionCount` and `sessions` (start, seconds, activity)                                |
| `GET /learn/cohorts/:cohortId/activity.csv?from&to&tz`              | `text/csv` (UTF-8 BOM), one row per session: learner, email, `start_utc` (ISO), `date_local`, item, `minutes` (1 decimal). More than 100,000 rows is refused with 413 and a message to narrow the range |

Learner: `GET /learn/me/cohorts/:cohortId/activity?from&to&tz` -> `LearnerActivityReport` for the caller only.

Averages (`CohortActivityReport.averages`), over the range: `perLearnerSeconds` (total / every learner listed, including those with no time), `perActiveLearnerSeconds` (total / learners with time), `perActiveDaySeconds` (total / (learner, day) pairs with time), `activeLearners`, and `learnersPerDay` (learners active on a day, averaged over every day in the range, one decimal). Nothing divides by zero. The page shows them first as 'Average per learner', 'Average per active day' and 'Active learners'.

Reports aggregate in SQL (`GROUP BY`) for a cohort; one learner's sessions are read row by row (one learner, at most 366 days). Rows with 0 seconds (a session opened and never given time) are not counted or listed. Learners see a notice on their course page that active time is recorded, never what they type.

The Activity page (`/lms/activity/:cohortId`): the cohort page has an 'Activity' button beside its title; the learner table links each name to the learner record (`/lms/cohorts/:cohortId/learners/:userId`, built separately) and has a 'Daily log' button that opens the per-learner daily table in one click, with sessions expandable per day. The button reads 'Download CSV'.

## 7. Cohort delivery

`delivery` is `online | live | hybrid` on `CohortListItem`/`CohortDetail`, accepted on `POST /learn/workspaces/:ws/cohorts` and `PUT /learn/cohorts/:id` (default `online`, 400 on anything else). The cohort details form has a select. The Attendance panel mounts for `live`/`hybrid`; the Activity link is always on the cohort page.

## 8. Limits and known gaps (decided or open)

- Case managers get none of this (they are read-only outcome readers). To change, edit `PROVIDER_STAFF_ROLES` and `COHORT_STAFF_ROLES` in `provider-access.service.ts`.
- Activity days follow the viewer's timezone, so two staff in different timezones can see a late session on different days. A session that crosses local midnight counts on its start day; a tool row is still split at UTC midnight when it spans it.
- Provider staff who are not members of a cohort's host organization cannot open that cohort's attendance or activity (roster rule); they reach talent data through the provider scope.
- `DataAccessLog` has no retention policy and no foreign keys. Deleting a user removes their notes and profile but leaves the audit rows (ids only).
- No email notifications (no email service yet).
